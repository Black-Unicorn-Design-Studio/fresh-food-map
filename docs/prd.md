# Product Requirements Document — Fresh Food Map

**Status:** v1 · **Last updated:** 2026-09-13 · **Licence:** AGPL-3.0-or-later for the code, ODbL for the dataset — see [`REUSE.toml`](../REUSE.toml) · Companion docs: [TRD](./trd.md), [style guide](./style-guide.md)

## 1. Overview

Fresh Food Map is a free, open-source app (iOS, Android and web) that helps people discover farmers markets near a given location. Three tabs — map, list, submit — one dataset, and a submission pipeline that ends in a pull request.

This document owns **scope**: who it is for, what ships, and what is deliberately absent. [The TRD](./trd.md) owns how it is built, and where the two touch — what merging means, the shape of the pipeline — it is canonical and this document links to it rather than restating it.

**There are no accounts**, and that is a product decision before it is a technical one. Nobody ever needed one to find a market, and submitting no longer asks who you are.

Market listings come from two kinds of source, and only one of them is running:

- **Community submissions**, through the Submit tab. **Working.** Three of the eight markets in `data/markets.json` arrived that way — batched into a pull request by the intake service and merged by a human.
- **Public open datasets** — OpenStreetMap first, then state and city open-data portals; the USDA Local Food Portal was researched and ruled out on licensing and on shape ([`scripts/ingest/README.md`](../scripts/ingest/README.md)). **Not written.** No normalizer exists yet, so the other five records were hand-assembled and carry `source: "manual"`.

Neither source publishes itself. Every record, seed or submission, reaches the dataset through a pull request a person reviewed and merged — that review is the check, and there is no second state a market can earn. All eight records in `data/markets.json` got there that way ([TRD §3](./trd.md#3-what-merging-means)).

### Problem statement

Farmers market information is fragmented and frequently stale. Public datasets exist but are incomplete and rarely surfaced in a consumer-friendly way; Google Maps listings are often wrong about seasonal schedules. Shoppers want one answer to: *"Which markets are near me and when are they open?"*

### Goals

1. Let anyone find farmers markets near a location in under 10 seconds, on any device — with no account and no backend involved. That is not merely the default path but the only one: there is no account to create and no database to be down.
2. Keep the app cheap to run and cheap to fork — near $0/month at hobby scale on free tiers, app-store fees excepted. The constraint that matters is that a *forker* can run the whole thing for nothing. There is exactly one server, the submission intake service (§6), and a fork that only wants the map does not have to run it, because the dataset is a file.
3. Maintain a high-quality, openly licensed, verifiable dataset that outlives the app itself.
4. Be genuinely contributable: a new contributor can run the whole stack locally for free.

### Non-goals

- **Accounts.** No sign-in, sign-up, sessions, roles, permissions or user database. This is a boundary of the product, not a stage of it: everything a person does here is either anonymous (find a market, submit one) or happens on GitHub under an account this project neither issues nor owns (review and merge).
- **Payments, in any form.** No paid tier, no billing, no subscriptions, no ordering, no ticketing, no donations plumbing. Everything the app does, it does for free and without an account. The distinction matters to a forker: what you receive is the whole thing, with nothing held back from it.
- **Reviews, ratings and social features.**
- **Vendor-level detail** — individual stalls, product inventories, vendor storefronts. The unit of the dataset is the market, and a market is a place with hours, not a directory of businesses.
- **Real-time occupancy** or "is it busy now".
- **Countries the app has not been taught.** Internationalization itself is no longer a non-goal — it shipped, for the United States, the United Kingdom and Jamaica: three address grammars, per-country units and opening frames, a per-market timezone, and a country setting that also narrows the dataset. What stays deliberately bounded is the *list*. `src/constants/countries.ts` is a closed vocabulary and CI rejects anything outside it, because a country code here is a promise the app can render that record correctly, not a label on it. A fourth country is a pull request that arrives with the composer, the unit, the centre, the box and some data already done — never a one-line enum edit. This entry used to read "structure for it, don't build it", and it is recorded here as changed rather than deleted, because it was a real decision that a real trip overturned.

## 2. Users

Four kinds of person, and none of them signs in to anything this project runs.

| Persona | Needs | State |
|---|---|---|
| **Shopper** (primary) | Find markets near me; see days and hours and season dates; narrow to the kind of market I want, or to the ones trading right now (§3); get directions. Never needs an account, and discovery works with no backend configured at all. | **Built** — and it is the whole of the running app, since there is no signed-in state a guest could be distinguished from. Place search, which was the gap, is built on both screens (§3). |
| **Submitter** (anyone, no account) | Report a missing market and be finished — no sign-up, no session, no status page to come back to. Accepts that the reply, if any, arrives on a public pull request rather than in an inbox. | **Built.** Submit tab → intake service → queue → batched pull request → merge. Three markets have made that trip. A build with no `EXPO_PUBLIC_INTAKE_URL` says so on the tab and points at the repository instead. |
| **Reviewer** (holds commit rights, works on GitHub) | Read a batched pull request, judge each item, edit or drop what's wrong, and merge. | **Built by not needing building**: reviewing is reading a pull request. Needs a GitHub account and nothing else — no server access, no admin UI, no role grant. It is deliberately the only human gate in the system, and merging is the vouch — there is no second step, so what reaches the file is what this person was willing to put their name on. |
| **Data consumer** (secondary) | Download the published dataset (GeoJSON), with each record's source attribution attached, for their own projects. | **Built.** One tier, so what a consumer downloads is the whole truth rather than half of it. |

That list is exhaustive on purpose. There is no curator, no admin and no vendor, because each of those names a permission and permissions need accounts to hang off. The judgement a curator would have made still happens — on a pull request, by whoever holds commit rights.

## 3. Core user stories

### Discovery

- As a shopper, I can see a map of markets around my current location, with permission. **Built** — and searching for a place is **built** too, on both screens: the filter panel's `NEAR` mode geocodes a town, address or postcode and uses it as an origin, so the map frames it with the nearest market and the list sorts from it. It cost little because the camera and the sort were already written against an arbitrary point; the device was simply the only thing that had ever supplied one. It inherits the geocoder's constraint: Nominatim forbids client-side autocomplete, so it is type-then-press and can never be as-you-type.
- As a shopper, I can browse the same markets as a list, sorted by distance. **Built.**
- As a shopper, I can tap a market to see details: the name, then its tags — each with an `ⓘ` *inside the chip* that opens the line explaining it — then the address, which is itself a link into a map app, the days and hours, the season, and links to directions and to the market's own website. **Built.** From the list a tap opens that screen directly; from the map a pin opens a summary card first, with `VIEW DETAILS` for the rest (§4). The screen names no source — per-record attribution is no longer displayed anywhere (§4) — and it ends with `Flag or update this listing`, which is the only route a reader has for saying a listing is wrong or should change.
- As a shopper, I can narrow the list to markets carrying a tag — `producer-owned`, for instance — because "is this growers selling their own food" is the question people actually arrive with. Selecting two tags narrows rather than widens (AND). **Empty is two different things:** a tag nothing in the current view matches shows a count of zero instead of disappearing — chips vanishing under a finger mid-selection is worse than a greyed one — while a tag *no market in the dataset carries* is not offered at all, since no state of the filters would make it show anything and the set cannot change while somebody is using it. A selected tag is always drawn, whichever rule would otherwise hide it, or a refresh could strand a filter nobody can switch off. **Built on both the list and the map**, from one `TagFilter` component, so neither view can narrow to something the other cannot reach — on both, a panel that stays closed until a 44 pt sprout disc opens it — docked bottom centre on the map and below the control row on the list, and on both the chips size to their own labels and break where they fall, so a wide page takes every chip it draws on one line and a phone falls to a ragged two-or-so per line — every chip it draws being the tags the dataset actually uses, which is two of the six today. They were pinned to two equal columns below 768 and one below 360; that grid and its breakpoints are gone, because word-width chips stop the longest label wrapping inside a chip too narrow for it outright, and a ragged row is a better trade than a broken one. One arrangement in both places rather than a grid here and word-width pills there, at the price of hit targets that are no longer uniform. The panel stays shut to start because the chips and their counts were otherwise the first thing under the heading on either screen, ahead of the controls people actually reach for. A market's tags appear on its detail screen and in both filter panels, each with an `ⓘ` opening the one-line description from `src/constants/tags.ts` (`src/components/tag-info.tsx`); the list card still doesn't carry them. The gloss used to be printed under every tag on the detail screen and is a press away now, which trades a taller block for a shorter one and puts the same explanation somewhere it never was — beside the filters, where somebody is choosing between the tags rather than reading one. **It is a disclosure and not a tooltip**: hover does not exist on a phone, React Native has no tooltip primitive, and the web's `title` attribute never reaches the DOM through react-native-web's prop allowlist — so the explanation opens on a press, stays until it is closed, and sidesteps WCAG 1.4.13 rather than trying to satisfy it. Which tags the set should hold stays open (§7).
- As a shopper, I can narrow the list to markets trading right now. **Built on both screens** (`isOpenNow`, `src/lib/markets.ts`), as the first chip in the filter panel's row, over one piece of state shared through `useFilters` — turn it on in either place and both agree. It was list-only, a switch beside the distance sort, on the grounds that the map had no such *control* — so sharing the state would have filtered pins by something with nothing on that screen to see or unset it. Putting the switch in the map's own filter panel is what retired the objection; the panel itself was already there. The tag counts are still computed with it applied, and it now sits in the row it governs, so no chip promises two markets over an empty list. It reads the *market's* clock, not the device's: every record carries an IANA timezone and `marketClock` (`src/lib/market-clock.ts`) resolves the question in the zone the stalls are standing in. It used to read the device, which was right only while the reader stood in the same zone as the thing they were looking at — three hours out for California reading Maryland, five for Manchester, and with Jamaica it is now zero for half the year and one hour for the other half, since America/Jamaica keeps no daylight saving. The one case left is a record with no zone at all, which only an out-of-date CDN copy can produce: that falls back to the device rather than refusing to answer. A market with no hours listed is never open, because absent hours are unknown hours and guessing optimistically sends somebody to a closed car park. A season running November to March wraps the new year rather than reading as an empty range. **Not built:** "open this weekend" (§4).
- As a shopper, the map and listings work offline-tolerantly: the dataset is bundled and cached, so a flaky connection still shows markets. **Built.**

### Contribution and review

Built end to end: form → intake service → queue → an agent batches into a pull request → a human merges. The shape and the reasoning are [TRD §4](./trd.md#4-the-submission-pipeline).

- As anyone at all, with no account and no sign-up, I can report a missing market: name, address, coordinates (looked up from the address, filled in from my current location, or typed), website, opening days with hours — one pair for all of them, or a pair per day behind a switch — tags, and a free-text note. I get no status page and no email; the reply, if there is one, is a public pull request. **Built**, per-day hours included: "Sat 8–1, Wed 3–7" is an ordinary market and used to survive only as prose in the note, where it reached the dataset solely if a reviewer retyped it. Pin-drop on a map and season dates are still **not** on the form — a reviewer reads those out of the note.
- As a submitter, I am refused mechanically and immediately if I trip the honeypot, submit faster than the configured minimum (two seconds today), send something malformed, exceed the rate limit, or send a market already in the file under the same name within 100 m — that last one because CI rejects it anyway, so accepting it would only fail a pull request I could not fix. Never refused on a judgement, because no judgement happens on the server.
- As a reviewer, I get a pull request holding a batch of submitted markets, with the ones that tripped a soft check called out by name in the body and sitting in the same diff as everything else. The agent flags; it does not hold back. I decide by editing the diff and merging.
- As a reviewer, I can see each submitter's note in the pull request body, as context for review — it is not published into the dataset.
- As a reviewer, merging *is* my vouch: what I merge is what the app publishes, with nothing downstream to catch a mistake and no second state to park a doubtful record in. So I say in the pull request how I know, and drop what I can't stand behind.
- As anyone, I can see what the policy is — batch size, rate limits, dedupe radius, flag list — because it is a committed config file (`intake.config.json`), and I can argue with it by opening a pull request against it.
- As a submitter, I can suggest a correction to an existing market. **Not built** — no field on the form, no path through the service, nothing half-finished either way (§7).

## 4. Feature scope

**This section owns the feature list.** If another document disagrees about whether something ships, this one is right.

### What v1 is

Discovery, filtering — by tag and by whether a market is trading right now, on both screens — and submissions that end in a pull request. v1 is a release tag to be cut from `main` once these are true, not a branch, so nothing below sits on a separate line of development. Each item says whether it exists today.

- **Map view** (MapLibre + OpenFreeMap tiles) with market pins. **Built** — one mark for every market (`src/constants/sprout.ts`), because no per-listing state exists for a second mark to carry and none should be invented for one. **Pressing a pin opens a summary card anchored to that pin, and pressing the same pin again closes it** — the pin is the card's only handle on the map, so the thing that opened it is what a reader reaches for to put it away; `📍 NEAR ME` opens the nearest market's card along with framing it, because "near me" is a question about a market rather than about the camera — name, town, whether it is open now, the week strip and any tags, with `VIEW DETAILS` for the rest. Anchored, not docked: the card was first drawn over the map's own controls, which was simpler and wrong, because eight identical pins and one card in the middle of the screen leave the reader matching a name against a map. It is one component on both platforms — the web map portals it into a `maplibregl.Popup`, the native map hands it to a MapLibre `Marker` — and **it reorients rather than hanging off the screen**: above the pin where there is room, below it near the top edge, and hooked to its own left or right corner near a side. That took a fix on each platform, for opposite reasons: the web popup chooses its own anchor but was choosing it before React had filled it, so it measured an empty box; the native marker never chooses at all, so the rule is written out in `placeCallout` (`src/lib/callout-anchor.ts`) and unit-tested. It used to navigate straight to the detail screen, which answered the second question before the first: the expensive thing to get back to on this screen is the map itself, a camera somebody framed and filters somebody set, and spending it to read three opening days was a poor trade. Pin clustering at low zoom is **not built** — neither map component clusters anything; the threshold that would trigger it is in [TRD §9](./trd.md#9-budgets).
- **List view** with sorting by distance or name, in either direction, and the **market detail screen**. **Built.** The list's controls read across **one row**, split to its two edges: the sprout disc that opens the tag filters at the left, and at the right `SORT`, a button that opens the four orders the list can be in (closest first, furthest first, name A to Z, name Z to A). The markets follow beneath. `🕒 OPEN NOW` used to sit at the right of that row beside `SORT`, and has moved into the filter panel, **inline with the tag chips and always first among them**: it was the one control that removes markets while sitting outside the box that holds the others, with a control that merely reorders between them. It sat on a line of its own for an hour in between, which made a set of one — it narrows the list exactly as a tag does, so it belongs in the row, and first because it asks about the whole list (is it trading today) where each tag asks about a kind of market. It wears a `highlight` border — neon purple — on and off alike, and the tag chips beside it wear `tint` the same way while `📍 NEAR ME` wears `locator`, so an edge anywhere in that row is identity and never state. What sets the clock filter apart is that its colour is nobody else's. **It is on the map too now**, in the same position in the same row, reading the same shared state: turn it on either place and both agree. It was list-only on the grounds that the map had no such control — putting one there is what retired the objection. **The two disclosures open independently** — pressing `SORT` no longer closes the filter panel, and the sprout disc no longer closes the sort list. They used to, on a height argument; what it missed is that the panel is a place you work and sorting is something you do to the result while you are still in it, so closing one to use the other threw away what the reader was in the middle of. The panel itself now spans the page rather than hugging its contents: measured to its widest child it came out 299 pt on a 390 pt phone, and the two-column grid inside that box left `Producer-owned` wrapping inside a chip sized for one line. Stretching the panel was the first answer to that; word-width chips (§3) are what settled it, and what the stretch still earns is a search field that cannot collapse into a slot and a left margin shared with every card below. It was two rows until they were merged — a second line of a phone's height for controls that fit on one, with the one you press first sitting at the bottom of the pair. Sorting was a switch and a pair of direction arrows before that, two controls splitting a single question between them. The count is not in the row, and the two screens no longer put it in the same place. On the map it is centred at the foot of the filter card, the only surface that screen has. On the list it has a centred line of its own, between the header band and the first market card: it spent a while at the foot of the panel there too, which put it in the one place it could not be read from — shut, which the panel is most of the time. Both read `8 markets`, and the fuller sentence ("1 of 8 markets shown") is spoken from an off-screen live region that stays mounted whether the panel is open or shut.
- **Open now.** **Built, on both screens** — the first chip in the filter row on the list and on the map, sharing one piece of state so the two tabs cannot disagree about it. Judged in the market's own timezone, which the dataset now records per record, and a market with no hours is never open. It was list-only until the map gained a filter panel to put it in. "Open this weekend" is still **not built** (§3).
- **Sorting from somewhere you are not.** **Built** on the list: the search box's `NEAR` mode takes a town, address or postcode, geocodes it on an explicit press, and sorts the markets by distance from there — cards show distances from that point rather than from the device. It answers "I will be in Athens next week, what is near there?", which no amount of device location can. **On the map the same mode frames that place with the nearest market** rather than sorting — the identical origin, spent on a camera instead of an order (§3). `🔎 Find it from the address` geocodes what is already typed, fills latitude and longitude, and shows the address it matched so it can be corrected. `📍 Use my current location` goes the other way and fills all three: it used to leave the address blank, so somebody standing in the market still had to type where they were standing. It never overwrites an address already typed. The pair is still required, because the feature schema needs a Point geometry and a record without one cannot merge; what changed is that nobody has to produce one. Requiring a coordinate people do not have was the fourth required field in all but name — the one §4's "resist adding a fourth" rule exists to prevent — and this is the cheapest way to stop paying for it without loosening the schema or moving a judgement onto the server.
- **"Use my location".** **Built** — on the map it frames the shopper and the nearest market together rather than zooming to a fixed level, because the nearest market is however far away it is and a fixed zoom left the answer off the edge. The nearest is taken from the filtered set, so the frame follows the tag filters instead of going stale behind them and never fits to a market the filters exclude; with nothing left to frame it just centres on the shopper. The same frame answers a geocoded place: `NEAR` sets the origin and the camera does the rest, which is what made place search a small change rather than a feature.
- **Tag filtering.** **Built.** The vocabulary is closed and lives in `src/constants/tags.ts` (`producer-owned`, `accepts-snap`, `indoor`, `organic-focus`, `grocery-store`, `donations-available` — the last two added after UAT asked for them, and a reminder that a market type is a product decision made by pull request rather than a free-text field); the validator rejects anything outside it, so a typo fails CI; the dataset carries the key on every record; the list and the map both filter on it with live counts, sharing one component; the Submit form offers all six, mapping the whole vocabulary rather than a chosen subset of it; and the detail screen lists a market's tags with a line explaining each. Two of the eight markets carry a tag today. The vocabulary itself is a product decision and not a settled one (§7).
- **Reporting a listing that is wrong.** **Built** — `Flag or update this listing`, a link at the foot of the detail screen, opening a prefilled issue against the repository (`reportUrl` in `src/constants/source.ts`: the name in the title, the id in the body). Before it, a reader who spotted bad hours had nowhere to put that, which sat badly against a design whose recovery path for everything else is "a person edits the file". It is deliberately **not** routed through the intake service: a correction naming an existing market is a same-name-within-100m duplicate, which intake hard-fails and drops in silence, so a report sent that way would vanish while its sender was told "received". The cost, stated rather than hidden, is that it wants a GitHub account — which is why it is a quiet link and not a button beside `GET DIRECTIONS`.
- **Attribution.** **Built, and no longer per record on screen.** Every record still carries `source` and `source_ref` in the file, so a data consumer downloads provenance along with the data. What the app renders is the collection-level ODbL credit on the list (`src/components/attribution.tsx`); the detail screen's source overline and closing credit line are gone, so per-record source is displayed nowhere. Two reasons, and both are the point: the ODbL credit now sits where nobody has to tap to reach it, and a source line beside a single listing is one reading away from a grade.
- **No per-listing grade.** The trust badge, the `verified`/`verified_at` fields and the verified-only filter are **retired, not pending** — removed from the code and from the dataset. The property schema is strict, so a `verified` key re-added by an unpatched writer fails CI loudly rather than merging unnoticed. Everything in the file is there because a person read the pull request and merged it, so there is no second state to sort listings into ([TRD §3](./trd.md#3-what-merging-means)).
- **Bundled dataset** (GeoJSON) with over-the-air refresh from a CDN. **Built** — `EXPO_PUBLIC_DATA_URL`, and unset means bundled-only, which is what a fresh checkout gets. It is the only data tier there is.
- **Submission → pull request.** **Built, and it has run.** A public form with no account; an intake service applying schema, honeypot, timing and hashed-IP rate-limit checks; a queue (SQLite, or a branch in the repository for hosts with no disk); and a batching agent that opens the pull request a human merges. One batch of three markets has been through it.
- **Web app.** **Built** — static export, `app.json` sets `web.output: "static"`. A web manifest ships in `public/`; there is **no service worker**, so it is **not installable** as a PWA ([TRD §6](./trd.md#6-platform)).
- **iOS and Android from the same codebase.** The code runs on both — MapLibre's native module is not in Expo Go, so a dev build is needed — but **no store build has been made**. EAS is configured (`eas.json`) and pointed at `freshfoodmap.app`; nothing has been built or submitted.

### Post-MVP (v1.x candidates)

- Correction suggestions on existing markets (§7 — a scope call, not a half-built feature).
- Favorites / saved markets (local-first).
- "Open this weekend" — open *now* is built, on both screens (above). This is the same schedule and season data read over a range rather than at an instant, and nothing reads it that way yet.
- Market photos (needs storage and a moderation policy before it needs code).
- Localization.

## 5. Success metrics

Hobby-scale project; metrics are directional and collected without invasive analytics (§6):

- Time-to-first-result under 10s on a mid-range phone over 4G.
- Dataset completeness, countable from `data/markets.json` at any commit: the share of markets carrying days and hours (8 of 8 today), season dates (2 of 8) and a website (7 of 8). Hours decide whether a listing is worth showing at all, and now also whether the open-now filter can say anything about it — a market with none is never open — so that share is a bar to hold rather than a number to grow. A bulk import is where it would slip.
- Median time from a submission arriving to a decision on its pull request under 7 days. One batch has been through the pipeline so far, which is a sample of one rather than a trend.
- External: forks and consumers of the open dataset; contributor pull requests merged. The repository is private today, so these start at zero by construction and only become measurable when it opens.

## 6. Constraints & assumptions

- **Cost ceiling:** free tiers by default, and a fork must remain runnable at $0/month at hobby scale — that is the load-bearing half, and it is a promise to forkers rather than a budget. Discovery is a static file and map tiles, so a fork that only wants the map runs no server at all and needs no keys. Only accepting submissions costs anything, and the intake service is small enough to sit on a cheap VPS or a container with no volume ([`server/README.md`](../server/README.md); both queue backends run side by side in the compose file). Paid items remain Apple Developer ($99/yr) and Google Play ($25 once), and are deferrable — web ships first.
- **A server is acceptable; a decision on it is not.** The intake service is a custom server, with its own disk and its own deploy. The rule it lives under is narrower than "no custom server, ever" and matters more: **no human decision happens on the server.** It validates mechanically and opens pull requests; every judgement call happens on GitHub, so reviewing is never gated on server access, and losing the server loses pending submissions rather than the project.
- **Single codebase** for all three platforms (Expo / React Native + react-native-web). Accepted trade-off: web is less SEO-optimal than a dedicated site; revisit only if market-page SEO becomes a goal.
- **No Google Maps dependency** — the billing-account requirement conflicts with the low-cost and open-source goals.
- **Data licensing:** ingested sources must permit redistribution; OSM-derived data keeps ODbL attribution. Every record carries its source.
- **Privacy:** on the discovery path a user's location never leaves the device except as a map viewport — the map frames it and the distance sort measures from it, both locally, and neither sends a point anywhere. There is one exception and it is on the submit form: `📍 Use my current location` reverse-geocodes the coordinates to fill the address field, so on that press the position does leave, as a point, to Nominatim ([TRD §7](./trd.md#7-security) carries the full account, including the `app.json` permission string, since rewritten, that now names both halves — the location that stays on the device and the address that does not). A fork that wants no third party there repoints `EXPO_PUBLIC_GEOCODE_URL` or drops the button; the coordinate fields still work. No third-party trackers and no analytics SDK. The only thing the project stores about a person is a salted hash of an IP bucket — and the intake service keeps it in two places, not one: the rate-limit window, which expires after a day (`retention_days.rate_limit`), and a column on the queued submission itself, which does not. `prune()` only drops submissions marked `rejected`, a status nothing ever sets, so a hash stays beside its payload for as long as the queue lives. Scrubbing it at `markBatched()` is the fix; until then this is the one place the service holds who submitted what.

## 7. Open questions

- **The Submit form states no licensing terms, and probably should state something.** What a submitter is told today is one sentence — that no account is needed, that the market is reviewed by a human, and that it is "published as open data anyone can reuse". That is true, and it is not terms: it names no licence and asks for no agreement. One half of the problem has since closed itself: the opening line now ties publication to the ask, reading "published as open data anyone can reuse — please leave out personal details". That warning began as a caption under the note field — the only field whose text is quoted verbatim into a pull request — and moved up so it is read before anyone types rather than only by whoever reaches the last field. The half that remains is the licence. The legal need for a grant is weak — the dataset is ODbL ([`REUSE.toml`](../REUSE.toml)) and market records are facts rather than authored work, which is exactly why a data-only pull request is exempt from the DCO ([TRD §8](./trd.md#8-testing-and-ci)). The product question is separate and live: does someone handing us a fact deserve to know, before they press the button, which licence it lands under? The two candidate answers cost very different amounts — a line of text under the button, or a checkbox that gates submission, which reintroduces a consent step on a form whose whole virtue is that it asks for nothing.
- **Which tags exist, and who decides.** Two parts are settled in code and should stay settled: the vocabulary is **closed** — a list in `src/constants/tags.ts` that the validator enforces, so adding a tag is a pull request people can argue about rather than a string somebody typed — and every tag must be **checkable from the market's own listing**, because an uncheckable tag is a claim wearing the clothes of a fact. What is open is the vocabulary itself and its custody: the current six are a starting guess — `grocery-store` and `donations-available` joined them in UAT, which is the process working rather than a settled vocabulary — and nobody has decided what earns a seventh or retires one, and the answer to "who decides" is whoever reviews the pull request — which is either exactly right or a gap, depending on how many people that is. Related: the Submit form lets a submitter tick tags, and nothing yet says whether a reviewer is expected to check them before merging.
- **Whether corrections to existing markets are in scope at all.** Nothing carries them — no form field, no service path, no schema — so this is a plain scope call rather than a half-built feature waiting to be finished.
- **Moderation policy** (what a reviewer is expected to reject). There are no sign-ups, so this is not about who may participate; it is about what a reviewer refuses on a pull request, which is a public decision with the submitter's text sitting in the diff.
- **Naming: register the trademark.** Under AGPL the code is freely forkable, so the name and the mark are the only things a fork cannot take. Check for collisions and register before store submission, not after. (The repo directory is still `fff`, deliberately — the rename went through the product, not the path.)
